# Function criteria — the detailed judgment

One axis behind every verdict: **does this function do ONE thing, honestly?** A function should have a single reason to change, take inputs it reads (not inputs it secretly writes), and not fork its own behavior on a flag its caller passes. If a function needs the word "and" to describe it, it does more than one thing.

## The one-thing test (the master decision)

Operative question: *can I state what this function does in one clause, with no "and", no "if the flag is set", and no hidden write?*
- **Yes** → it does one thing → `clean`.
- **No** → it mutates a borrowed input, forks on a flag, is never called, or mixes concerns → flag the specific rule below.

Everything below is this one test applied to specific shapes. Resolution is two-stage (see the SKILL's Hard Rules): stage 1 tests each rule's own trigger and drops any rule whose trigger is unmet or whose inputs are unavailable; stage 2 takes the topmost fired row. The per-rule uncertainty test runs in stage 1, before precedence — so a weak F3 and a strong F5 never race: whichever rules actually fire are ranked, and if only one fired that is the verdict.

**What each rule's stage-1 inputs are** (so "inputs unavailable" is not read differently per agent): **F2, F3, F5 need only the body** — the mutation, the fork, and the IO/compute boundaries are all visible in the body; call sites are irrelevant to these verdicts, so a missing call site never drops them. **F4 needs the body PLUS the caller's completeness assertion** — absent the assertion, F4's input is unavailable → it drops. No rule requires call sites to be supplied.

The rules are language-agnostic — examples use TypeScript, but a Python function mutating its list argument fails F2 and a Go function with a `test bool` parameter fails F3 just the same. Arg-count is deliberately absent here — see the boundary section.

## F2 — No output arguments

A function should not write through a parameter it did not create. Reading an input is honest; mutating it is a side effect the caller can't see at the call site. Return a new value instead.

```ts
type Report = { content: string };

// Bad — mutates the argument the caller owns
function appendFooter(report: Report): void {
  report.content += "\n---\nGenerated by System"; // caller's object changed silently
}

// Good — returns a new value; input untouched
function withFooter(report: Report): Report {
  return { ...report, content: `${report.content}\n---\nGenerated by System` };
}
```

The trigger is objective and anchored to a single citable test — **is the mutated state's allocation visible anywhere in the function/class under judgment?**
- **Allocated in-scope on any path → owned → not F2.** A local the function `new`s, a class-body field initializer (`entries: string[] = []`), or a field assigned a fresh value in the constructor (`this.store = []`) — all citable, all owned. Where the allocation sits (initializer vs constructor body vs local) does not matter; that it is citable in-scope does.
- **Every assignment path sources the field from a caller-supplied parameter → caller-allocated → F2.** `this.store = injectedStore` mutated later is F2: the caller owns that array.
- **Mixed case, explicit tie-break:** if ANY assignment path allocates in-scope (e.g. `this.entries = seed ?? []`, where `?? []` is an in-scope allocation), the state is owned → not F2. Caller-allocated (F2) requires that EVERY path sources it from a parameter.
- **Allocation not citable anywhere in the supplied scope → unresolved → stage-1 uncertainty → drop → `clean`.**

(F2 reads the body and any in-scope allocation site; call sites are not required.)

Boundary: F2 flags the hidden WRITE. Whether the input should be `readonly` or a different shape is `ts-types`. If the *name* lies about the effect (e.g. `getConfig` that creates), that's `clean-names` N7 — resolve name-honesty overlaps to N7.

## F3 — No flag arguments

A boolean or enum parameter that forks the body means the function does at least two things. Split it; let the call site name which one it wants.

```ts
// Bad — one function, two behaviors, caller reads `render(true)` and learns nothing
function render(isTest: boolean) {
  if (isTest) renderTestPage();
  else renderProductionPage();
}

// Good — two functions, each does one thing
function renderTestPage() { /* ... */ }
function renderProductionPage() { /* ... */ }
```

The trigger is the body, observed at one point: **a boolean/enum parameter forks THIS body into ≥2 behaviors** — whether the call site passes a literal (`render(true)`) or a variable (`render(computeMode())`) makes no difference, the fork is in the body either way. A flag merely stored, forwarded, or passed to a well-known API (not forking THIS body) is the sole exemption. A discriminated-union parameter that a `switch` dispatches on is a signature/type choice → defer to `ts-function-signatures` / `ts-types`, not F3.

## F4 — Delete dead functions

If nothing references it, it is dead. No "just in case" code — version control preserves history.

```ts
// Bad — defined, exported nowhere, called nowhere
function legacyFormatV1(input: string) { /* ... */ }

// Good — deleted. It is recoverable from git if ever needed.
```

The trigger is objective AND gated on an explicit input: **no reference exists AND the caller asserted the search scope is complete** (e.g. "whole-repo search done, these are all references"). "Supplied scope" is not inferred from what you happen to see — a lone function with no visible callers is the PARTIAL-scope case unless completeness was asserted, so it degrades to `clean`. Two exceptions that are NOT dead even under a complete scope — do not flag F4:
- **Entry points / framework hooks** — `main`, a route handler, a lifecycle method, a test, an event callback. Called by the runtime, not by name in the code.
- **Public export contract** — an exported symbol of a library/package whose consumers are outside the supplied scope.

No completeness assertion, or partial scope → you cannot prove it's dead → `clean`.

## F5 — Single responsibility

A function should have exactly one reason to change. Mixing levels of abstraction — fetching, transforming, and rendering in one body — is the common shape.

```ts
// Bad — three reasons to change: the query, the tax rule, the email format
async function processOrder(id: string) {
  const order = await db.query("SELECT * FROM orders WHERE id = ?", id);
  const total = order.items.reduce((s, i) => s + i.price, 0) * 1.21;
  await mailer.send(order.email, `Total: ${total}`);
}

// Good — each does one thing; processOrder composes them
const loadOrder = (id: string) => db.query("SELECT * FROM orders WHERE id = ?", id);
const totalWithTax = (order: Order) => order.items.reduce((s, i) => s + i.price, 0) * 1.21;
const sendReceipt = (order: Order, total: number) => mailer.send(order.email, `Total: ${total}`);
```

The trigger must be citable, not a feeling: **the body contains ≥2 distinct IO/compute boundary lines you can point at.** In `processOrder` that is line 77 (DB read — IO), line 78 (tax math — pure compute), line 79 (email send — IO): three boundaries, so `F5`, and those same lines ARE the suggested split boundary. If you cannot cite the boundary lines — one cohesive operation, no shift you can point to — resolve to `clean`. SRP is the easiest rule to over-apply, so an uncitable boundary drops the rule in stage 1.

## F1 — Arg-count is NOT judged here

"Too many arguments / too many props" is a real smell, but the threshold and the fix are language- and framework-specific, so this judge does not own it.

- **TypeScript** → `defer-signature`, hand off to `ts-function-signatures` (positional vs options object, defaults, overloads-vs-unions). It already owns the "3+ params → options object" rule; duplicating a number here would let the two skills diverge.
- **Any other language** → emit `defer-signature` and name the concern ("many parameters, several optional") but do NOT invent a number. What counts as too many differs by language and call-site ergonomics.

## Verdict quick reference

| Verdict | Principle | Fix direction |
|---------|-----------|---------------|
| F2 | No output args | return a new value, don't mutate the input |
| F3 | No flag args | split into two named functions |
| F4 | No dead code | delete it (unless entry point / export contract) |
| F5 | Single responsibility | split at the abstraction-level shift |
| defer-signature | Arg-count | TS → `ts-function-signatures`; else name it, no number |
| clean | One thing, honest inputs, alive | — |

## The boundary (what clean-functions does NOT judge)

Behavior/shape (F2–F5) is language-agnostic. Arg-count and all type/signature concerns are the TypeScript deferral; the name is always `clean-names`. Applying the split/delete is always the actor's job.

| Concern | Authority |
|---------|-----------|
| Does the function do ONE thing, honest inputs, alive (F2–F5) | **clean-functions** (any language) |
| Whether the NAME reveals/matches intent (incl. name-vs-effect honesty, N7) | `clean-names` (any language) |
| How many args / positional vs options / defaults / overloads (F1) | `ts-function-signatures` (TypeScript) |
| What type/shape a parameter or return should be | `ts-types` (TypeScript) |
| Applying the split, delete, or return-instead-of-mutate | `leave-it-cleaner` (the actor) |

Philosophy: **a function that does one thing needs no "and" to describe it.** If your summary has an "and", that's the split boundary.
